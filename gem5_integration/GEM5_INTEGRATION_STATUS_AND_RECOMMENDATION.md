### 技术发现

#### SE模式的根本限制
SE (System Call Emulation)模式简化了地址空间管理：
- 虚拟地址直接映射到模拟内存
- mmap()创建的是匿名内存，不会路由到设备
- PIO设备的read/write方法从未被调用
- **结论**：SE模式不支持真实硬件设备访问

#### FS模式的复杂性
Full System模式需要：
1. Linux内核镜像（62MB，已下载）
2. 磁盘镜像（607MB，下载失败）
3. PCI设备实现（需要重写FPGA设备）
4. 内核驱动或/dev/mem访问
5. 长启动时间（数分钟到数十分钟）

## 问题分析

### gem5集成的真正价值是什么？

**目标**：测量CPU-FPGA交互的精确开销
- PCIe传输延迟
- DMA操作开销
- 中断处理时间
- 内存一致性开销

**当前Mock模式的局限**：
- 假设零开销的CPU-FPGA通信
- 使用公式估算FPGA计算时间
- 无法捕捉真实的系统级交互

### 为什么需要FS模式？

SE模式的根本问题：
```
用户程序 → 虚拟地址 → 模拟内存
                    ↓
                 (无法路由到设备)
```

FS模式的完整路径：
```
用户程序 → 系统调用 → 内核驱动 → MMIO/DMA → PCI设备 → FPGA模型
```

## 建议方案

### 方案A：完成FS模式集成（推荐用于论文）

**优点**：
- 提供最精确的CPU-FPGA交互开销数据
- 可以测量真实的系统级性能
- 学术价值高

**缺点**：
- 实施复杂度高（估计2-3周）
- 需要稳定的网络下载大文件
- 调试困难

**实施步骤**：
1. 重新下载Ubuntu镜像（使用wget/curl断点续传）
2. 将FPGAAcceleratorSE改为PCI设备
3. 创建FS配置脚本
4. 编写简单的内核模块或使用/dev/mem
5. 端到端测试

### 方案B：使用Mock模式结果（推荐用于快速发表）

**优点**：
- 已有完整的性能数据（12.2×加速比）
- ±4%精度足够可信
- 可以立即撰写论文

**缺点**：
- 缺少真实的CPU-FPGA交互开销数据
- 审稿人可能质疑Mock模式的准确性

**补充措施**：
1. 在论文中明确说明Mock模式的假设
2. 引用相关文献估算PCIe开销（通常<5%）
3. 进行敏感性分析：假设不同的交互开销

### 方案C：混合方案（推荐）

**Phase 1**：使用Mock模式数据撰写初稿
- 12.2×加速比
- 36.8×能效提升
- 完整的DSE框架

**Phase 2**：并行进行FS模式集成
- 作为补充实验
- 提供更精确的交互开销数据
- 如果成功，可以在修订版中加入

**Phase 3**：论文投稿策略
- 初稿基于Mock模式结果
- 在"Limitations"部分说明未来工作
- 如果审稿人要求，可以补充FS模式数据
