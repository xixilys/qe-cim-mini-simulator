# QE Workflow-to-FPGA DSE Method Design

Status: algorithm-design baseline after `alg-iter-001`.

This document defines the current target method for a DAC-grade QE
Workflow-to-FPGA DSE paper.  It is not a completion claim.  It identifies the
algorithm, its required evidence, and the current gaps between the target method
and the repository implementation.

## Method Name

**WAMF-DSE:** Workflow-Abstraction-Guided Multi-Fidelity Deployment DSE.

The intended contribution is not generic multi-fidelity search.  The thesis is:

> Workflow abstractions expose fidelity-mismatch modes in scientific FPGA
> deployment, and using those abstractions to guide promotion improves
> expensive-evaluation efficiency compared with kernel-only, SCF-only, generic
> BO, and generic Pareto search.

## Problem Statement

Given a QE workflow workload `w`, search a deployment design space `X` and
choose a small set of FPGA deployment candidates that are Pareto competitive
under latency, energy, EDP, resource pressure, data movement, feasibility, and
implementation risk.

The method must decide both:

- which deployment candidate `x in X` should be considered next; and
- which fidelity `f in F` should be used to observe or validate it next.

The output is not a single speedup number.  It is:

- a Pareto set of deployment plans;
- per-plan architecture, mapping, schedule, offload, memory, and implementation
  parameters;
- model predictions and uncertainty;
- promotion trace and calibration history;
- implementation-package handoff for final candidates;
- explicit limitations and evidence requirements for any final performance
  claim.

## Inputs

The primary input is a QE workflow bundle or corpus containing:

- stage descriptors for QE programs and workflow steps;
- input files, logs, profiles, and runtime metadata;
- dimensions such as `nbnd`, `npw`, FFT grids, k-points, spin, and iteration
  counts;
- per-stage and per-kernel timing when available;
- artifacts such as save directories, wavefunctions, charge density,
  eigenvalues, forces, stress, restart metadata, post-processing outputs, and
  file sizes;
- dependency edges, restart/reuse edges, branch/merge structure, and control
  barriers;
- correctness observables and tolerances.

Current repository status: the implementation handles a useful `pw.x`-centric
subset and some post-processing labels, but not the full target contract.

## Outputs

For each selected candidate the method should produce:

- candidate identity and deployment parameters;
- stage-region placement and offload boundary;
- memory residency and transfer/synchronization plan;
- estimated objectives at each available fidelity;
- posterior uncertainty or confidence intervals;
- blockers and implementation feasibility risks;
- next recommended fidelity action;
- implementation package refs when selected for HLS/Vivado handoff.

## Variables

- `W`: workload corpus.
- `G_w`: typed workflow graph for workload `w`.
- `S`: workflow stages.
- `K`: compute kernels or compute regions.
- `D`: data/artifact objects.
- `X`: deployment candidate space.
- `x`: one deployment candidate.
- `F`: fidelity ladder.
- `f`: one fidelity action.
- `B`: total expensive-evaluation budget.
- `y_f(x,w)`: objective vector observed or predicted at fidelity `f`.
- `c_f(x,w)`: cost of evaluating candidate `x` at fidelity `f`.
- `p_feas(x,w)`: feasibility probability.
- `u(x,w)`: predictive uncertainty.
- `m(x,w)`: workflow-mismatch risk features.
- `P_t`: current Pareto frontier estimate after iteration `t`.

## Workflow Abstraction

Target graph:

```text
G_w = (V_stage, V_compute, V_data, E_control, E_data, E_artifact, E_reuse)
```

Required graph semantics:

- typed stages, not only SCF;
- explicit branch, fan-out, fan-in, restart, and reuse edges;
- stage-specific repetition semantics:
  `scf_loop`, `nscf_single_spectrum`, `ionic_relax_loop`,
  `cell_relax_loop`, `post_processing_pass`, `dfpt_qpoint_loop`, and
  `external_workflow_stage`;
- stage-local compute features instead of duplicated global kernel weights;
- data-object lifetimes and residency constraints;
- host-control and synchronization barriers;
- correctness observables attached to stages and workflow outputs.

Current gap:

- The repository can build workflow graphs and feature contracts, but parts of
  the graph are still linearized and scalarized.  `alg-iter-001` identified
  stage-order fallback and stage-local weight contamination as immediate
  semantic risks.

## Deployment Grammar

Candidate `x` is not a fixed row.  It is generated by a grammar:

```text
x = (
  architecture_template,
  compute_region_selection,
  offload_boundary,
  mapping_granularity,
  runtime_schedule,
  data_residency,
  memory_topology,
  microarchitecture_knobs,
  implementation_knobs,
  precision_policy
)
```

Minimum grammar axes:

- architecture template: HBM streaming, DDR streaming, hybrid CPU control,
  FFT/transpose pipeline, tiled local memory;
- compute-region selection: stage, stage cluster, kernel callsite, dataflow
  subgraph;
- offload boundary: workflow hotspot bundle, stage cluster, kernel bundle,
  host-only retained stages;
- schedule: sequential, overlapped DMA/compute, batched stage pipeline,
  double-buffered, multi-kernel concurrent;
- residency: host-resident windows, HBM-resident hot arrays, checkpoint reuse,
  hybrid host/device cache;
- memory topology: DDR, HBM channels, BRAM/URAM/PLRAM locality, bank binding;
- implementation knobs: stream width, burst length, unroll factors, II target,
  array partitioning, DMA depth, clock target, platform/part constraints;
- precision policy: FP64 strict first, mixed precision only after tolerance
  review.

Current gap:

- The repository has broad high-level axes, but lacks enough kernel-specific
  FPGA microarchitecture and package-level implementation knobs for a strong
  deployment DSE claim.

## Fidelity Ladder

The method treats fidelity as an action dimension:

| Fidelity | Role | Claim Strength |
| --- | --- | --- |
| `L0` legality and static feasibility | prune impossible candidates | no performance claim |
| `L1` analytical workflow model | broad search and cheap ranking | projection only |
| `L2` TLM/SystemC-like Python model | refine timing/data movement | model evidence only |
| `L3` generic-sim/SystemC/gem5 samples | independent timing/calibration | calibration evidence |
| `L4` HLS C-sim/C-synth/RTL sim | implementation feasibility | kernel-level tool evidence |
| `L5` Vivado implementation/bitstream/board | final FPGA deployment evidence | claim-specific evidence |

Evidence serves promotion and calibration.  It is not the search objective.

## Surrogate Model

The surrogate predicts residuals over cheap models:

```text
r_f(x,w) = log(y_f(x,w)) - log(y_L1(x,w))
```

Recommended model:

- graph encoder over workflow and candidate placement;
- residual heads for latency, energy, data movement, resource pressure, and
  EDP;
- feasibility head for legality and implementation risk;
- uncertainty estimate from deep ensemble, Laplace, conformal calibration, or
  Gaussian-process residual model where data scale allows;
- pairwise/listwise ranking head for top-k promotion quality.

Neural networks are support modules.  They are not evidence and not the main
contribution unless independent labels and OOD validation are strong.

## Search State

At iteration `t`, state contains:

- workflow graph and deployment grammar;
- candidate pool or candidate generator state;
- observed tuples `(x, f, y_f, feasible, cost)`;
- posterior predictions and uncertainty;
- calibration residuals between fidelities;
- current Pareto estimate;
- budget remaining;
- blockers for unavailable or invalid fidelity actions.

## Action

The action is:

```text
a_t = (x_t, f_t)
```

This is stricter than selecting a candidate list.  The algorithm must justify
why the next expensive unit is spent on that candidate at that fidelity.

## Acquisition Rule

The first target acquisition is:

```text
A_t(x,f) =
  p_feas(x,w)
  * [ EHVI_t(x)
      + lambda_u U_t(x)
      + lambda_m M_t(x,w)
      + lambda_d D_t(x)
    ]
  * VOI_t(f | x,w)
  / Cost_t(x,f)
```

Where:

- `EHVI_t(x)` is expected Pareto/hypervolume improvement.
- `U_t(x)` is calibrated uncertainty.
- `M_t(x,w)` is workflow-mismatch value: host-control pressure, data lifetime,
  synchronization, post-processing, branch/reuse, transfer pressure, and
  implementation-risk axes that are likely to make L1 wrong.
- `D_t(x)` rewards design diversity under scarce observations.
- `VOI_t(f | x,w)` estimates the value of observing fidelity `f`, including
  expected uncertainty reduction and calibration reuse for nearby candidates.
- `Cost_t(x,f)` accounts for runtime/tool cost and opportunity cost.

Current gap:

- The current policy has deterministic weighted terms and fixed metadata-driven
  fidelity scoring.  It should evolve toward posterior-driven value of
  information and calibrated uncertainty.

## Pseudocode

```text
Input:
  workflow corpus W
  deployment grammar Gamma
  fidelity ladder F
  budget B

Output:
  Pareto deployment set P
  evaluation trace T
  calibrated model state M
  implementation handoff set H

1. For each workload w in W:
     G_w <- build_workflow_graph(w)
     Q_w <- extract_workflow_mismatch_features(G_w)

2. X0 <- generate_initial_candidates(G_w, Gamma)
   X <- legality_filter(X0)

3. Evaluate all or many x in X with L1 cheap model.
   Initialize posterior M from L1 features and any seed observations.

4. T <- {}
   while budget remains:
       for each admissible action (x, f):
           predict y_f(x,w), uncertainty, feasibility
           estimate EHVI, workflow mismatch value, VOI, and cost
           score A_t(x,f)

       if no admissible action remains:
           stop with blockers

       choose a_t = argmax A_t(x,f)
       y <- run_or_request_fidelity(a_t)
       T <- T union {(x,f,y)}
       update residual surrogate and fidelity calibration
       update Pareto frontier estimate
       update candidate generator or local neighborhood if supported

5. H <- select final Pareto candidates with implementation feasibility.
   Generate implementation packages for H.
   Return P, T, M, H.
```

## Failure And Blocker Semantics

- `blocked_missing_workflow_semantics`: workflow graph cannot represent needed
  stage/data/control facts.
- `blocked_no_stage_local_weights`: stage-local compute weights are missing or
  contaminated by global aggregate weights.
- `blocked_candidate_illegal`: candidate violates grammar or platform rules.
- `blocked_fidelity_prerequisite`: requested high fidelity lacks required lower
  fidelity, correctness vector, source, script, or tool.
- `blocked_tool_unavailable`: required tool path is unavailable.
- `projection_only`: model result exists but cannot support final hardware
  claims.
- `trusted_for_calibration`: independent fidelity result can calibrate lower
  models.
- `trusted_for_claim`: claim-specific correctness and implementation gates are
  satisfied.

## Innovation Boundary

This method is not:

- MAESTRO/ZigZag/Timeloop-style kernel/layer mapping alone;
- HLS pragma tuning after a fixed kernel is chosen;
- generic BO or NSGA-II over a flat parameter vector;
- a QE GPU port;
- evidence-matrix completion.

The intended novelty is:

- workflow-mismatch-aware promotion for scientific FPGA deployment;
- search over workflow offload boundaries and data-residency decisions;
- joint candidate/fidelity selection with calibration reuse;
- residual surrogate conditioned on workflow graph and deployment grammar;
- implementation handoff that keeps host/control/data movement in accounting.

## Evidence Plan

| Question | Evidence Required |
| --- | --- |
| Does workflow abstraction matter? | Ablations without DAG, data lifetime, host-control/sync, post-processing, and correctness pressure. |
| Does search beat baselines? | Equal-budget curves versus random, manual, NSGA-II/III, BO/EI, Hyperband, L1-only, kernel-only. |
| Does it avoid mispromotion? | Promoted/non-promoted samples checked against independent L3/L4/HLS/Vivado feedback. |
| Are models calibrated? | Rank correlation, ECE/calibration curves, residual error by workflow class, top-k recall. |
| Is deployment feasible? | Golden vectors, HLS C-sim/C-synth, Vivado timing/utilization/power, host-inclusive timing. |
| Is QE abstraction credible? | Measured multi-workload QE corpus with artifacts, logs, dimensions, timings, and correctness observables. |
